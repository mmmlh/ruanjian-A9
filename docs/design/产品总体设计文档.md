## 一、需求分析

### 1.1 项目背景

随着物联网（IoT）技术的快速发展，智能家居已从概念走向现实。然而，当前智能家居面临三大核心问题：

1. **生态碎片化**：不同品牌的智能设备使用各自专属 APP，用户需安装多个应用
2. **数据安全隐患**：家庭隐私数据经云端传输，存在泄露风险
3. **标准不统一**：缺乏统一的操作系统底座，跨品牌联动困难

OpenHarmony 作为国产分布式操作系统，天然具备"万物互联"的基因。本项目基于 OpenHarmony 构建统一的智能家居设备控制系统，实现对灯光、空调、门禁等设备的一站式管理。

### 1.2 赛题要求分析

根据赛题说明，需实现以下核心功能：

| 功能模块 | 要求 | 优先级 |
|----------|------|--------|
| **控制中心** | 设备联动 + 场景管理 | P0（必做） |
| **照明中心** | 远程开关 + 人体感应 + 定时场景 | P0（必做） |
| **温湿度控制中心** | 实时监测 + 多品牌空调控制 | P0（必做） |
| **智能门禁** | 远程开关 + 状态监控 | P0（必做） |
| **安全机制** | 传输加密 + 数据加密 + 密钥安全存储 | P1（加分） |
| **服务卡片** | 桌面快捷查看设备状态 | P2（鸿蒙原生特性加分） |

### 2.2 分层架构

| 层级 | 技术 | 职责 |
|------|------|------|
| **展示层** | ArkTS + ArkUI | 用户界面、状态管理、手势交互 |
| **通信层** | HTTP / WebSocket / MQTT | REST API 调用、实时推送、设备指令 |
| **业务层** | FastAPI + Python | 认证授权、规则引擎、品牌适配、数据加解密 |
| **数据层** | SQLite + WAL 模式 | 用户/设备/房间/规则/日志 持久化存储 |
| **设备层** | Python 模拟器 | 传感器数据生成、设备状态机、MQTT 通信 |

### 2.3 技术选型理由

| 技术 | 选择理由 |
|------|----------|
| **OpenHarmony + ArkTS** | 赛题要求；分布式的软总线能力；Stage 模型更现代化 |
| **FastAPI** | 高性能异步 Python 框架；自动生成 Swagger 文档；类型安全 |
| **MQTT** | IoT 标准协议；低带宽/低功耗；发布/订阅模式天然适配设备通信 |
| **SQLite** | 轻量无需独立服务；WAL 模式支持并发读；适合中小规模部署 |
| **Mosquitto** | 轻量级 MQTT Broker；Docker 化部署；支持 TLS |
| **Docker Compose** | 一键部署；服务隔离；环境一致性 |

### 2.4 MQTT Topic 设计

| Topic 模式 | 方向 | 说明 |
|------------|------|------|
| `home/{room_id}/{device_type}` | — | 设备基础主题 |
| `home/{room_id}/{device_type}/command` | APP→设备 | 控制指令下发 |
| `home/{room_id}/{device_type}/status` | 设备→APP | 设备状态上报 |
| `home/{room_id}/{device_type}/sensor` | 设备→APP | 传感器数据上报 |
| `home/{room_id}/{device_type}/response` | 设备→APP | 指令执行响应 |
| `home/#` | 后端订阅 | 全局监听（规则引擎） |

**示例**：
- 客厅灯控制: `home/livingroom/light/command`
- 卧室温度上报: `home/bedroom/temperature_sensor/sensor`
- 客厅门禁状态: `home/livingroom/door_lock/status`

## 三、技术方案

### 3.1 通信安全方案

采用**三层安全体系**：

```
第一层：传输加密 (MQTT over TLS / HTTPS)
    ↓
第二层：身份认证 (JWT Token, 24h 过期)
    ↓
第三层：数据加密 (AES-256-CBC, 密钥嵌入 JWT)
```

#### 3.1.1 JWT Token 设计

```json
{
  "sub": "1",
  "username": "admin",
  "role": "admin",
  "aes_key": "<base64-encoded-32-byte-key>",
  "exp": 1234567890,
  "iat": 1234560000
}
```

- 密钥: HS256 + 服务端密钥签名
- 有效期: 24小时
- AES 密钥: 随机生成，嵌入 Token 分发给客户端

#### 3.1.2 AES 加密流程

```
发送:
  明文数据 → PKCS7填充 → AES-256-CBC加密(随机IV) → Base64编码 → 发送

接收:
  Base64数据 → Base64解码 → AES-256-CBC解密(提取IV) → PKCS7去填充 → 明文数据
```

### 3.2 多品牌空调适配

采用**统一指令模型 + 品牌翻译器**模式：

```
APP 统一指令                     品牌专属指令
  {"power":"on",       → 格力: {"power":"PWR_ON",
   "mode":"cool",              "mode":"MODE_COOL",
   "temp":24,                  "temp":"TEMP_24",
   "fan":"auto"}               "fan":"FAN_AUTO"}
                          → 海尔: {"power":"POWER=1",
                                  "mode":"MODE=COOLING",
                                  "temp":"SET_TEMP=24",
                                  "fan":"FAN=AUTO"}
                          → 美的: {"power":1,
                                  "mode":2,
                                  "temp":24,
                                  "fan":1024}
```

支持品牌：格力(gree) / 海尔(haier) / 美的(midea) / 通用(generic)

### 3.3 规则引擎设计

```
传感器事件 → Topic解析 → 状态缓存更新 → 规则遍历匹配 → 动作执行
                                    ↓
                            condition_json 评估
                              - trigger: 传感器类型
                              - field: 数据字段
                              - operator: eq/neq/gt/lt/gte/lte
                              - value: 阈值
                              - and: 附加条件列表
```

**预置规则**：

| 规则 | 触发条件 | 执行动作 |
|------|----------|----------|
| 人来开灯 | PIR 有人 + 灯关闭 | 开灯(亮度80%) |
| 人走关灯 | PIR 无人 + 灯开启 | 关灯 |
| 高温制冷 | 温度 > 28°C + 空调关闭 | 开空调(制冷26°C) |
| 高湿除湿 | 湿度 > 80% + 空调关闭 | 开空调(除湿模式) |

### 3.4 设备模拟器设计

所有模拟器继承自 `BaseDevice` 基类：

```
BaseDevice(ABC)
├── connect_mqtt()        # 连接 Broker
├── handle_command()      # 抽象：处理控制指令
├── generate_data()       # 抽象：生成模拟数据
├── publish_status()      # 发布设备状态
├── publish_sensor_data() # 发布传感器数据
└── _run_loop()           # 模拟主循环
```

**数据生成策略**：
- 温度传感器：正态分布 N(25, 0.5)，范围 [15, 38]
- 湿度传感器：正态分布 N(55, 5)，范围 [20, 95]
- PIR 传感器：10-30秒随机切换有人/无人
- 灯光/空调/门禁：被动响应指令，不主动产生数据

## 七、项目亮点与创新

1. **鸿蒙原生特性**：基于 OpenHarmony Stage 模型，利用 ArkTS + ArkUI 声明式开发
2. **三层安全体系**：TLS + JWT(嵌入AES密钥) + AES-256-CBC，从传输到数据全方位保护。所有设备控制指令的 action 和 params 整体加密传输
3. **多品牌空调适配**：统一指令模型 + 品牌翻译器，支持格力/海尔/美的
4. **可扩展规则引擎**：JSON 配置的条件-动作规则，支持热加载
5. **仿真先行策略**：17个设备模拟器，无需硬件即可全链路演示
6. **Docker 容器化**：4容器一键部署，适合快速交付
7. **统一遥控器设计**：1个页面支持5种设备类型(灯光/空调/门禁/窗帘/加湿器)，根据设备类型动态渲染不同遥控面板
8. **设备管理**：支持添加/编辑/删除设备，8种设备类型可选
9. **数据监控**：传感器实时数据 + 历史记录 + 操作日志三Tab页面
