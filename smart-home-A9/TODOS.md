## 独立多厂商、多协议设备生成器

> 状态：未来方向，当前不实施
>
> 优先级：待后续版本评估
>
> 目标语言：Python

### 背景

当前 `cloud/simulators` 已包含温度、湿度、人体感应、灯、空调、门锁、窗帘和加湿器等 MQTT 设备模拟器。现有后端通过以下主题接收遥测、同步状态并下发控制指令：

```text
home/{room}/{device_type}/{sensor|status|response|command}
```

当前实现适合固定演示环境，但仍存在以下限制：

- 模拟设备在代码中静态创建，无法通过配置或接口动态生成。
- 除空调指令映射外，厂商差异尚未形成独立适配层。
- 设备发现依赖静态候选目录，不是由在线模拟设备主动上报。
- 主题仅包含房间和设备类型，同一房间无法可靠区分多台同类型设备。
- MQTT 是唯一实际接入协议，尚不能验证 HTTP、WebSocket 或网关协议的接入流程。
- 缺少可重复场景、故障注入、命令回执关联和协议异常模拟。

### 总体目标

创建一个独立于现有后端和 `cloud/simulators` 的 Python 设备生成器。它应能批量创建不同厂商、型号、设备类型和协议的虚拟设备，并完整模拟服务器发现设备、绑定设备、接收遥测、下发控制、接收回执以及感知设备离线的过程。

生成器采用“双平面”结构：

1. **管理平面**：通过 REST API 和 CLI 创建、查询、启动、停止设备，运行场景并注入故障。
2. **设备平面**：通过 MQTT、HTTP、WebSocket 或虚拟网关适配器，让模拟设备按照真实设备的行为与服务器通信。

### 设计边界

- 生成器作为独立 Python 包和独立进程运行，不导入后端内部模块，也不直接读写后端数据库。
- 核心运行时只维护设备生命周期、状态机、遥测调度和命令执行，不包含厂商或协议特有分支。
- 设备行为、厂商映射和协议传输均通过注册表加载，新增实现不应修改核心调度器。
- 设备运行状态以生成器内存为准；配置和可重复场景可以从文件加载，但不在第一阶段引入新的持久化数据库。
- Zigbee、BLE、Matter 等协议先模拟协议语义和网关行为，不声称兼容厂商私有协议或真实无线网络。
- 真实硬件、射频适配器和官方厂商云账号不作为第一阶段依赖。

### 设备 Profile

每台设备由 YAML 或 JSON profile 定义，并在加载时通过统一 schema 校验。profile 至少包含：

| 字段 | 含义 |
|---|---|
| `device_id` | 全局唯一、稳定的设备标识 |
| `vendor` | 厂商标识，例如 `gree`、`haier`、`midea`、`xiaomi`、`aqara`、`tuya` |
| `model` | 厂商型号或模拟型号 |
| `device_type` | 灯、空调、门锁、窗帘、插座或传感器等类型 |
| `protocol` | `mqtt`、`http`、`websocket`、`zigbee_gateway`、`ble_gateway` 或 `matter_gateway` |
| `room` | 服务端使用的房间标识 |
| `firmware_version` | 公告消息中使用的模拟固件版本 |
| `capabilities` | 支持的动作、属性、量程和只读能力 |
| `initial_state` | 启动后的确定性初始状态 |
| `telemetry` | 采样间隔、取值范围、分布、变化速率和随机种子 |
| `faults` | 离线、延迟、丢包、错误回执和非法载荷等故障规则 |

首批 profile 应覆盖至少三家厂商、三种设备类型和三种协议适配方式。厂商名称只表示行为和载荷差异的模拟样例，不表示已接入其官方协议。

### 组件划分

- **Profile Loader**：加载 YAML/JSON，校验唯一 ID、能力定义、状态类型、数值范围和协议配置。
- **Device Runtime**：管理 `created`、`starting`、`online`、`offline`、`stopped` 和 `faulted` 生命周期。
- **Behavior Registry**：按设备类型加载状态机，例如灯光亮度、空调模式、门锁授权和传感器采样。
- **Vendor Registry**：在统一动作与厂商载荷之间进行双向转换，未知厂商回退到 `generic`。
- **Protocol Registry**：为 MQTT、HTTP、WebSocket 和虚拟网关提供统一的连接、发布、订阅和断开接口。
- **Scenario Runner**：使用固定随机种子和虚拟时间运行可重复的环境变化、联动和故障场景。
- **Management API/CLI**：负责设备批量编排，不直接代替设备平面传输控制指令。

### 管理平面接口

REST API 的最小能力如下，CLI 使用相同的应用服务：

| 方法与路径 | 用途 |
|---|---|
| `POST /api/v1/devices/batch` | 从 profile 或请求体批量创建设备 |
| `GET /api/v1/devices` | 查询设备配置、生命周期、连接状态和最近错误 |
| `GET /api/v1/devices/{device_id}` | 查询单台设备状态和最近一次通信 |
| `POST /api/v1/devices/{device_id}/start` | 启动设备并连接服务器 |
| `POST /api/v1/devices/{device_id}/stop` | 优雅停止设备并发布离线状态 |
| `POST /api/v1/devices/{device_id}/faults` | 注入离线、延迟、丢包、错误回执或非法载荷 |
| `DELETE /api/v1/devices/{device_id}/faults` | 清除故障并恢复正常行为 |
| `POST /api/v1/scenarios/{scenario_id}/run` | 按固定种子运行可重复场景 |

接口必须拒绝重复 `device_id`、无效 profile、未知协议、超出能力范围的初始状态和不受支持的故障类型，并返回稳定的机器可读错误码。

### 设备平面契约

新设备使用包含唯一设备 ID 的基础主题：

```text
home/{room}/{device_type}/{device_id}
```

在基础主题下定义：

| 后缀 | 方向 | 内容 |
|---|---|---|
| `/announce` | 设备到服务器 | 厂商、型号、协议、固件、能力和在线状态 |
| `/sensor` | 设备到服务器 | 传感器数据、单位、时间戳和数据质量 |
| `/status` | 设备到服务器 | 当前完整状态、在线状态和状态版本 |
| `/command` | 服务器到设备 | `request_id`、`action` 和 `params` |
| `/response` | 设备到服务器 | `request_id`、`success`、`state` 或错误码 |

MQTT 适配器应使用 retained `announce` 或等价机制支持发现，并通过 LWT 发布意外断线。HTTP 和 WebSocket 适配器必须表达相同的领域消息，不允许各自定义不同的设备状态语义。

兼容期内，MQTT 适配器可以为单实例设备启用旧主题模式；新主题是多实例设备的规范接口。服务端应同时解析新旧主题，但数据库中的新设备必须保存包含 `device_id` 的完整基础主题。

### 数据流

1. 管理平面加载并校验 profile，创建尚未连接的设备实例。
2. 设备启动后由协议适配器连接服务器并发布 `announce` 和初始 `status`。
3. 服务端将公告加入动态待绑定目录，绑定后按唯一 `device_id` 持久化设备元数据。
4. 设备按 profile 周期发布遥测；服务端更新状态、历史数据、规则和 WebSocket 推送。
5. 服务端发送带 `request_id` 的命令；设备校验能力和参数后执行状态转换。
6. 设备发布带相同 `request_id` 的成功或失败回执，并在成功时附带最新状态。
7. 超时、断线或错误回执由服务端明确记录，不能将“已发布”直接视为“设备已执行”。

### 测试要求

- **单元测试**：profile 校验、状态机、能力范围、厂商映射、协议注册、确定性随机数据和故障规则。
- **协议契约测试**：所有适配器针对同一组发现、遥测、控制、回执和离线用例运行。
- **MQTT 集成测试**：连接、重连、订阅恢复、retained 公告、LWT、QoS 和重复消息。
- **HTTP/WebSocket 集成测试**：认证失败、超时、断线、重连和服务端错误。
- **服务端集成测试**：动态发现、绑定、多实例寻址、状态同步、历史数据和命令回执关联。
- **Docker Compose 冒烟测试**：同时启动服务器、Broker 和生成器，完成发现到控制的完整闭环。
- **规模测试**：逐步提升设备数量和遥测频率，记录 CPU、内存、消息延迟和失败率。
