# A9 智能家居首轮真实功能化改造设计

## 1. 背景与目标

当前项目已经具备 OpenHarmony 客户端、FastAPI 后端、MQTT 消息链路、设备模拟器和基础测试，但用户体验仍然存在明显“空壳感”，主要体现在：

- 设备发现接口通过随机插入数据库伪造设备，不是真实候选设备接入流程。
- 设备管理页要求手工输入 MQTT topic，接入门槛高且不符合真实产品操作方式。
- 首页、遥控页、监控页虽然能展示部分数据，但缺少操作反馈、在线状态说明和完整闭环。
- 规则页要求用户手写 JSON，属于开发者视角，不是终端用户可用能力。
- 多个页面各自请求数据，但没有形成“接入设备 -> 控制设备 -> 观察状态 -> 配置联动”的完整业务链。

本轮目标是在保留现有项目骨架的前提下做一次中等重构，把系统从“演示 UI”改造成“可真实使用的智能家居控制原型”。

## 2. 改造范围

本轮覆盖以下五个模块：

1. 首页总览页 `DashboardPage`
2. 设备接入与管理页 `DeviceManagePage`
3. 设备遥控页 `DeviceRemotePage`
4. 数据监控页 `DataMonitorPage`
5. 规则编排页 `RulesPage`

同时配套调整后端以下能力：

- 设备发现/候选设备接口
- 已绑定设备与候选设备的区分
- 设备控制返回结构
- 首页摘要接口
- 规则创建辅助接口

本轮不做的内容：

- 不重写登录/注册体系
- 不推翻现有 MQTT 主题结构
- 不引入新的外部云平台
- 不做复杂图表库接入
- 不重做数据库整体模型，只做增量字段和查询整理

## 3. 总体设计原则

### 3.1 真实优先

所有展示型功能必须对应真实数据来源或真实业务动作。不能再出现“用户点击发现设备，系统随机造出设备”的行为。

### 3.2 闭环优先

每个关键页面都必须满足“看到当前状态 -> 执行动作 -> 得到成功/失败反馈 -> 看到状态变化”的闭环。

### 3.3 用户视角优先

把当前偏技术化的操作方式替换为面向普通用户的交互，例如规则创建改成表单编排，设备绑定改成候选列表选择。

### 3.4 兼容现有结构

保留 FastAPI 路由体系、OpenHarmony 页面结构、MQTT 驱动的状态同步方式，避免把项目改成全新系统，降低实现风险。

## 4. 核心业务流

### 4.1 设备接入流

1. 用户进入设备管理页
2. 客户端调用“候选设备发现接口”
3. 后端返回当前系统中可识别但未绑定的设备列表
4. 用户选择设备并绑定到某个房间，可顺带修改展示名称
5. 绑定成功后设备进入正式设备列表
6. 首页、遥控页、监控页立即可见该设备

### 4.2 设备控制流

1. 用户在首页或遥控页选择某台设备
2. 客户端发起控制指令
3. 后端统一通过服务调用接口落到设备命令执行层
4. 返回本次命令结果、目标实体、预期变更状态
5. 客户端显示“执行中/成功/失败”反馈
6. WebSocket 或主动刷新回收最新状态

### 4.3 数据观察流

1. 用户进入监控页
2. 页面分为实时概览、历史记录、操作日志三部分
3. 用户可按设备筛选
4. 页面展示当前值、最近变化和最近操作
5. 数据来自真实状态、真实传感器历史、真实命令日志

### 4.4 联动规则流

1. 用户进入规则页查看已有规则
2. 创建规则时通过“触发设备/条件/目标设备/动作/参数”的表单向导输入
3. 客户端把表单转换为后端要求的 `condition_json` 与 `action_json`
4. 后端保存规则并重新加载规则引擎
5. 规则列表以自然语言摘要显示

## 5. 后端设计

### 5.1 设备模型重组

当前问题是“发现”与“绑定”混在一起，发现接口直接写入 `devices` 表。本轮改为两层语义：

- 已绑定设备：已经出现在 `devices` 表，属于某个房间，可被控制和展示
- 候选设备：系统当前能识别到、但还没绑定到房间的设备

实现方式优先采用“基于现有状态源推导候选设备”，避免引入重型新表。候选设备来源按优先级如下：

1. 设备模拟器已上报状态但数据库中不存在对应 `mqtt_topic` 的设备
2. 规则/状态接口里可枚举但未绑定的实体
3. 如无实时候选，再返回空列表，而不是随机造设备

若实现过程中发现必须持久化候选设备，则新增轻量表 `discovered_devices`，字段包含：

- `id`
- `mqtt_topic`
- `type`
- `name`
- `brand`
- `status_json`
- `last_seen_at`
- `source`

只有在状态源无法稳定重复枚举时才落表。

### 5.2 设备发现接口改造

当前 `POST /api/discovery` 会随机创建设备，本轮改造为：

- `POST /api/discovery`
  - 扫描当前候选设备
  - 不直接写入正式设备表
  - 返回 `discovered` 列表与统计信息

- 新增或增强 `POST /api/bind_device`
  - 输入候选设备标识、房间 ID、展示名称
  - 执行绑定，将候选设备转入正式设备表
  - 绑定后返回正式设备信息

必要时补充：

- `GET /api/devices/unbound`
  - 返回最近发现但未绑定的候选设备

### 5.3 首页摘要接口

新增 `GET /api/dashboard/summary`，统一返回首页所需数据，减少客户端多次拼装：

- 房间列表及设备数量
- 已绑定设备列表
- 在线/离线数量
- 关键环境指标
- 最近操作日志
- 场景列表

在线状态判断规则：

- 若设备最近有状态更新时间，且在可接受时窗内，标记为在线
- 长时间未收到状态则标记为离线
- 无法判断时标记为未知，但前端仍展示

### 5.4 控制接口返回结构增强

当前 `/api/services` 只返回 `changed_states` 和 `service_response`。本轮补充更适合 UI 的返回结构：

- `success`
- `message`
- `entity_id`
- `action`
- `changed_states`
- `service_response`
- `executed_at`

失败时保证返回明确错误信息，前端可直接提示。

### 5.5 规则接口辅助能力

保留现有 `/api/rules` 存储结构，但增加两类辅助能力：

- 规则摘要生成逻辑
  - 后端或前端统一把 `condition_json` / `action_json` 转为自然语言
- 规则创建支持更稳定的字段约束
  - 客户端只能提交受支持的触发器、操作符、设备类型和动作

如有需要可新增：

- `GET /api/rules/options`
  - 返回可选传感器类型、可选目标设备、动作模板、默认参数

这能减少前端硬编码和错误输入。

## 6. 前端页面设计

### 6.1 首页总览页

首页改成“家庭态势页”，不再只是平铺设备卡片。

保留：

- 环境温湿度卡片
- 场景入口
- 房间筛选
- 设备卡片网格

新增或强化：

- 在线状态总览
- 最近操作摘要
- 空状态说明
- 操作后即时刷新
- 设备卡片中的状态文字规范化

首页数据来源优先切到 `dashboard/summary`，减少房间、设备、场景分散请求。

交互要求：

- 首页刷新时显示加载态
- 场景执行时按钮置灰并显示执行态
- 场景执行后显示结果提示并回刷设备状态
- 设备卡片点击后进入设备控制页并传入设备类型

### 6.2 设备管理页

设备管理页拆成两个区块：

1. 已绑定设备
2. 可接入设备

已绑定设备区支持：

- 查看房间、类型、在线状态
- 编辑名称和品牌
- 删除设备

可接入设备区支持：

- 扫描候选设备
- 查看候选设备最近状态
- 选择房间
- 一键绑定

删除当前手工填写 MQTT topic 的新增模式，原因是这会让普通用户承担内部实现细节。

若后端候选设备为空，页面明确提示“当前未发现可接入设备”，而不是自动编造。

### 6.3 设备遥控页

遥控页保留按设备类型区分的控制面板，但统一补齐以下能力：

- 顶部显示当前设备名、房间、在线状态
- 操作中的 loading 状态
- 操作成功/失败提示
- 命令去抖，避免滑块高频提交导致刷屏
- 操作完成后状态回读

各设备类型细化要求：

- 灯光：开关、亮度、颜色模式
- 空调：开关、温度、模式、风速
- 门锁：开锁/上锁、自动回锁倒计时、鉴权失败提示
- 窗帘：开/关/百分比位置
- 加湿器：开关、档位、目标湿度

无设备时显示引导文案，提示用户先到设备管理页绑定设备。

### 6.4 数据监控页

监控页改成三个页签，但信息表达更清楚：

- 实时概览
- 历史记录
- 操作日志

实时概览：

- 每个传感器显示当前值、更新时间、状态标签

历史记录：

- 支持“全部/按设备”筛选
- 显示值、单位、时间、设备名
- 无数据时显示空态

操作日志：

- 展示动作、目标设备、时间、结果摘要
- 优先展示最近控制事件与场景执行事件

### 6.5 规则编排页

规则页改造重点是去掉 JSON 直输。

新建规则表单结构：

- 规则名称
- 触发源
  - 温度传感器
  - 湿度传感器
  - 人体传感器
- 判断条件
  - 大于
  - 小于
  - 等于
- 阈值
- 目标设备
- 执行动作
- 动作参数

参数区根据目标设备和动作动态切换：

- 空调 `set` 时显示温度、模式、风速
- 灯光 `set` 时显示亮度、颜色
- 门锁通常只显示开锁/上锁，不暴露多余参数

规则列表展示：

- 规则名
- “如果……则……”摘要
- 启用/禁用开关
- 删除操作

## 7. 数据流与状态同步

### 7.1 客户端状态更新策略

状态同步采用“两段式”：

1. 用户操作后立即更新本地交互状态为执行中
2. 命令返回后主动刷新一次，并继续接收 WebSocket 推送

这样能兼顾响应速度和最终一致性。

### 7.2 WebSocket 使用边界

WebSocket 主要负责：

- 设备状态变化推送
- 传感器最新值变化推送

不负责替代所有初始数据加载。页面首次进入仍用 HTTP 获取完整快照。

### 7.3 离线与失败状态

当设备离线或后端执行失败时：

- 前端禁用高风险操作，或在点击时给出明确错误提示
- 控制结果不再只是 `console.error`
- 页面上保留最近一次错误消息，直到用户下一次成功操作或刷新

## 8. 错误处理设计

### 8.1 前端

每个页面都补充以下状态：

- `loading`
- `errorMessage`
- `successMessage`
- `emptyState`

错误展示原则：

- 接口失败时给出用户可理解的中文提示
- 空列表与请求失败分开表达
- 控制失败时保留当前状态，不假装成功

### 8.2 后端

后端接口错误统一返回：

- 明确 HTTP 状态码
- 可读的 `detail` 或 `message`
- 对输入错误给出可修复提示

特别处理：

- 绑定不存在的候选设备
- 为不存在的房间绑定设备
- 控制不存在或离线设备
- 创建不合法规则

## 9. 测试设计

### 9.1 后端测试

新增或调整以下测试：

- 设备发现不再随机插入正式设备
- 候选设备绑定成功后进入正式设备列表
- 首页摘要接口返回完整结构
- 设备控制接口返回成功/失败字段
- 规则创建支持表单映射后的 JSON

### 9.2 前端验证

由于 OpenHarmony 页面自动化成本较高，本轮以以下验证为主：

- 编译通过
- 关键页面无 ArkTS 类型错误
- 关键用户路径手工验证

关键路径包括：

1. 首页查看状态并执行场景
2. 在设备管理页扫描并绑定候选设备
3. 进入遥控页控制设备并观察反馈
4. 在监控页查看实时值、历史记录、日志
5. 在规则页创建、启停、删除规则

## 10. 实施顺序

建议按以下顺序实现：

1. 后端候选设备发现与绑定链路
2. 首页摘要接口与设备在线状态
3. 设备管理页重构
4. 遥控页闭环反馈
5. 数据监控页增强
6. 规则页表单化
7. 测试补全与联调

## 11. 验收标准

本轮完成后，应满足以下标准：

- 发现设备不会再随机造正式设备
- 设备接入流程不要求手输 MQTT topic
- 首页能真实反映设备、场景和环境状态
- 任意设备控制都有成功/失败反馈和状态回刷
- 监控页能看见真实实时值、历史值和日志
- 规则创建不需要手写 JSON
- 后端测试覆盖新增核心行为
- OpenHarmony 关键页面能正常编译运行

## 12. 风险与应对

### 风险 1：当前模拟器无法稳定产出“未绑定设备”

应对：

- 优先从现有状态流推导候选设备
- 如不稳定，再引入轻量 `discovered_devices` 持久化层

### 风险 2：OpenHarmony 页面状态管理较分散

应对：

- 先把 API 返回结构整理稳定
- 页面按模块逐一收口，不一次性抽大状态框架

### 风险 3：规则表单与后端 JSON 结构不完全匹配

应对：

- 限定本轮支持的触发器和动作范围
- 在前端做强约束，只生成后端可接受结构

## 13. 结论

本设计不追求把项目变成最终商用系统，而是把现有“可演示的壳子”推进成“可真实操作、可被检查、能说明业务闭环”的智能家居原型。第一轮完成后，系统将具备可信的设备接入、控制、监控和联动体验，能够经受更严格的代码与功能审查。
