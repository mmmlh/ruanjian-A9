# A9 中等重构版智能家居改造设计

## 1. 目标

本轮改造采用“中等重构版”路线：保留当前 `FastAPI + MQTT + OpenHarmony` 的整体架构，不推翻现有页面与数据库模型，但把系统从“可演示 UI”收敛为“具备真实设备接入、状态展示、控制反馈和规则编排闭环”的智能家居原型。

本轮重点借鉴 Home Assistant 的设计思想，但不机械照搬其完整架构。核心原则是：

- 以后端统一整理设备状态与能力，前端不再自行猜测设备控制方式
- 页面优先消费聚合后的“可渲染数据”，而不是拼接多个零散接口
- 所有控制动作都要有明确的成功/失败反馈，并能看到状态回刷
- 设备接入流程要符合用户视角，不再暴露内部 MQTT 细节

## 2. 本轮范围

### 2.1 覆盖页面

- `DashboardPage`
- `DeviceManagePage`
- `DeviceRemotePage`
- `DataMonitorPage`
- `RulesPage`

### 2.2 覆盖后端接口与服务

- 设备发现与绑定
- 首页聚合摘要
- 统一设备控制返回结构
- 监控页历史数据与日志接口
- 规则选项与规则创建辅助接口

### 2.3 不做的内容

- 不重写登录注册体系
- 不整体替换 MQTT topic 结构
- 不引入新的云平台或第三方设备生态
- 不做复杂图表系统
- 不在本轮引入完整的 Home Assistant 式 entity registry / device registry

## 3. 设计原则

### 3.1 保留现有骨架

继续使用当前仓库中的：

- FastAPI 路由组织
- MQTT 驱动的设备状态同步方式
- OpenHarmony 页面路由和 ArkTS 页面结构
- 现有 `devices`、`device_log`、传感器历史等数据库能力

### 3.2 后端统一抽象，前端消费结果

后端负责把设备类型、状态、能力、最近操作、在线状态转换成稳定的接口结构。前端不再分散地硬编码每一类设备的推断规则，只保留必要的交互呈现逻辑。

### 3.3 设备闭环优先

优先打通这条主链路：

`发现候选设备 -> 绑定到房间 -> 首页可见 -> 遥控控制 -> 状态刷新 -> 日志留痕`

### 3.4 规则能力适度表单化

本轮规则系统不追求高度通用，而是支持当前项目内已有设备类型和常见动作，先把“能稳定创建和执行”做好。

## 4. 目标架构

本轮将系统收敛为 4 个稳定层次。

### 4.1 设备状态层

真实状态源仍然来自：

- `devices.status_json`
- MQTT 上报后的状态更新
- 设备更新时间 `updated_at`

后端基于这些真实状态推导：

- 用户可读状态文本
- 在线 / 离线 / 未知
- 页面展示所需的关键指标

### 4.2 设备能力层

后端按设备类型维护统一能力描述，例如：

- `light`: `on/off/set brightness/color`
- `ac`: `on/off/set mode/temp/fan`
- `door_lock`: `lock/unlock`
- `curtain`: `open/close/set position`
- `humidifier`: `on/off/set level/target_humidity`

该能力描述用于：

- 遥控页控件生成与约束
- 规则页动作选项来源
- 控制接口参数校验

### 4.3 页面聚合层

后端为关键页面输出稳定的聚合结果：

- 首页：总览摘要
- 设备管理页：已绑定设备和候选设备
- 遥控页：设备详情与控制结果
- 监控页：实时值、历史记录、日志
- 规则页：触发器、操作符、目标设备、动作选项

### 4.4 交互闭环层

所有控制动作都返回统一结果结构，至少包含：

- `success`
- `message`
- `entity_id`
- `action`
- `changed_states`
- `service_response`
- `executed_at`

前端统一处理：

- loading
- success message
- error message
- 状态刷新

## 5. 后端设计

### 5.1 候选设备发现与正式绑定分离

当前问题是“发现设备”与“创建设备”语义混杂。本轮改成两步：

- `POST /api/discovery`
  - 只返回候选设备列表
  - 不直接写入正式 `devices`
- `POST /api/bind_device`
  - 把候选设备绑定到指定房间
  - 成功后写入正式 `devices`

候选设备优先来源：

1. 最近有状态上报，但数据库中尚未存在对应 `mqtt_topic` 的设备
2. 模拟器上报可推导出的未绑定设备
3. 其他可稳定识别但尚未绑定的实体

若现有状态流不足以稳定支撑候选枚举，再引入轻量持久化表；否则本轮尽量避免新增数据表。

### 5.2 首页摘要接口

统一由 `GET /api/dashboard/summary` 返回首页所需数据，至少包含：

- `rooms`
- `devices`
- `scenes`
- `recent_logs`
- `stats`

其中 `stats` 至少包含：

- `total_devices`
- `online_devices`
- `offline_devices`
- `total_rooms`
- `total_scenes`

在线状态判断基于 `updated_at` 与可接受时间窗口，不要求绝对实时，但要一致、可解释。

### 5.3 统一设备控制接口

设备控制继续走统一服务接口，但返回结构必须对 UI 友好。除成功路径外，也要保证失败时返回明确错误原因，典型场景包括：

- 设备不存在
- 设备类型不匹配
- 设备离线
- MQTT 分发失败
- 鉴权或解密失败
- 参数不合法

### 5.4 监控数据接口

监控页继续使用现有历史与日志接口，但要确保：

- 实时数据来自真实设备状态，而不是额外伪造
- 历史数据支持按设备筛选
- 日志数据支持按设备筛选
- 日志内容可被前端稳定解析和显示

### 5.5 规则选项接口

新增或稳定化 `GET /api/rules/options`，统一返回：

- 可用触发器
- 可用比较操作符
- 可用目标设备
- 每类设备允许的动作

规则保存格式可继续沿用当前 `condition_json` 与 `action_json`，但前端不再要求用户直接手写 JSON。

## 6. 前端页面设计

### 6.1 DashboardPage

目标是从“展示页”升级为“家庭总览页”。

页面应重点展示：

- 在线设备数 / 总设备数
- 温湿度关键环境指标
- 可直接执行的场景
- 最近操作日志
- 按房间筛选的设备卡片

交互要求：

- 设备卡点击时传递 `deviceId` 和 `deviceType`
- 场景执行后显示成功或失败反馈
- WebSocket 或主动刷新后能及时回刷设备状态
- 不只用颜色点表示状态，还要有人类可读文案

### 6.2 DeviceManagePage

页面定位为“设备接入中心”。

拆成两块：

- 已绑定设备
- 候选设备

已绑定设备至少显示：

- 设备名
- 类型
- 房间
- 品牌
- 在线状态
- 最近更新时间

候选设备至少显示：

- 设备名
- 类型
- 候选来源房间提示
- 最近状态摘要
- 在线状态

绑定流程要求：

- 先选择房间
- 可调整展示名称
- 一键绑定
- 绑定成功后正式设备列表立即刷新

### 6.3 DeviceRemotePage

页面定位为统一控制壳。

保留按设备类型区分控制面板，但统一补足：

- 顶部设备基础信息
- 在线状态与最近更新时间
- 操作中的 loading
- 成功/失败提示
- 控制后的状态回刷

具体要求：

- 滑块类操作要做轻度防抖，减少频繁提交
- 离线设备要限制高风险操作
- 门锁要区分认证失败与设备离线等不同错误

### 6.4 DataMonitorPage

维持三段式结构：

- `Live`
- `History`
- `Logs`

要求如下：

- Live：展示当前值、更新时间、基础状态
- History：支持按设备筛选历史记录
- Logs：展示控制日志、场景日志、规则触发日志

空数据、请求失败、加载中要分别呈现，不混为一个状态。

### 6.5 RulesPage

页面目标是表单化规则创建。

规则创建流程拆成：

- 规则名称
- 触发器选择
- 操作符选择
- 阈值输入
- 目标设备选择
- 动作选择
- 参数补充

要求：

- 列表页显示自然语言摘要
- 不同设备类型只展示允许的动作与参数
- 创建成功后刷新规则列表并清理表单残留状态

## 7. 公共模型与接口约定

### 7.1 ApiClient

`ApiClient` 负责：

- 统一解析后端错误信息
- 统一映射页面模型
- 统一解析控制结果

页面中尽量不重复拼接错误文案和字段转换。

### 7.2 设备模型

当前 `Device`、`DiscoveredDevice`、`DashboardSummary` 相关模型建议补充或稳定以下语义：

- 在线状态
- 状态摘要
- 最近更新时间
- 控制结果映射

这样能减少页面内部重复推断。

## 8. 实施顺序

建议按以下顺序推进：

1. 设备发现与绑定闭环
2. 首页摘要与在线状态
3. 统一设备控制返回
4. 监控页数据收口
5. 规则页表单化
6. 联调、测试与收尾

## 9. 任务包拆分

建议拆成 5 个任务包：

- 任务包 A：候选设备扫描、绑定设备、设备管理页接入
- 任务包 B：首页摘要接口、在线状态规则、Dashboard 对接
- 任务包 C：统一控制结果、遥控页闭环反馈、状态刷新
- 任务包 D：监控页实时值、历史记录、日志视图
- 任务包 E：规则选项接口、规则表单、联调和回归测试

## 10. 测试设计

### 10.1 后端测试

重点验证：

- discovery 不再直接插入正式设备
- bind_device 能把候选设备转换为正式设备
- dashboard summary 返回结构完整
- services 接口返回统一成功/失败结构
- rules options 返回的触发器、动作、目标设备与实际能力一致

### 10.2 前端验证

重点验证：

- Dashboard 正常加载并能执行场景
- DeviceManagePage 能扫描并绑定候选设备
- DeviceRemotePage 能控制设备并看到反馈
- DataMonitorPage 能看到实时值、历史记录、日志
- RulesPage 能通过表单创建规则

## 11. 验收标准

本轮完成后，应满足：

1. 扫描设备时不再随机写入正式 `devices`
2. 候选设备可绑定到房间并立即出现在设备列表
3. 首页能稳定显示在线状态、环境摘要、场景和最近日志
4. 任意设备控制后能看到明确成功或失败提示
5. 控制后设备状态可回刷，不再只有“命令已发送”
6. 监控页能看到真实实时值、历史值和日志
7. 创建规则不需要手写 JSON
8. 后端测试通过，关键 OpenHarmony 页面可编译运行

## 12. 风险与处理

### 12.1 候选设备来源不稳定

处理方式：

- 优先从真实状态流推导
- 只有在推导不稳定时才补轻量持久化

### 12.2 前端页面状态分散

处理方式：

- 优先稳定后端返回结构
- 再逐页统一 loading / error / success / empty 状态

### 12.3 规则表单与后端结构不完全一致

处理方式：

- 限制本轮支持的触发器和动作范围
- 由后端 options 提供权威约束

## 13. 结论

这份“中等重构版”设计的目标，不是把 A9 直接改造成完整的 Home Assistant，而是在保留你现有项目骨架的前提下，吸收其“统一设备抽象、聚合页面数据、控制闭环明确、用户视角接入”的优点。

完成本轮后，A9 将从“分散的页面与接口集合”收敛为一套更像真实智能家居系统的可验证原型，并且后续继续扩展设备、监控与联动时，改造成本也会更低。
