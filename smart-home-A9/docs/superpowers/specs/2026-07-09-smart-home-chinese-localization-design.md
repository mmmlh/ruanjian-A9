# smart-home-A9 全量汉化设计

## 目标

在不改变现有业务接口、数据库字段、机器码和测试契约的前提下，把 `smart-home-A9` 中用户实际可见的英文界面和提示统一汉化，并建立一层轻量的前端文案入口，避免后续继续汉化时文案再次散落到各个页面里。

本次汉化覆盖：

- OpenHarmony ArkTS 前端页面中的标题、按钮、状态词、空状态、加载提示、表单占位符、操作反馈、规则描述文案
- `ApiClient.ets` 中面向用户的网络错误和接口错误提示
- 后端 API 和服务层中会直接返回给前端展示的 `message`、应用标题、候选设备展示名/房间提示

本次汉化不覆盖：

- `rule_name_required`、`candidate_not_found`、`device_offline` 等机器码
- 接口路径、类名、字段名、数据库列名、日志内部标识
- 完整多语言框架、语言切换功能

## 背景与约束

当前仓库已经有较完整的前后端联动能力，但用户可见文案仍明显混杂中英：

- 前端多个页面直接内联英文字符串
- `ApiClient.ets` 同时承担接口访问和用户提示映射，错误提示尚未统一为中文
- 后端部分 `message`、应用标题、候选设备名称仍为英文
- 测试和前端逻辑已经依赖部分英文机器码，不能直接替换

因此，这次设计要同时满足两个约束：

1. 用户看到的结果尽量全中文
2. 内部契约尽量不变，避免把“汉化”做成“业务重构”

## 方案对比

### 方案一：页面内联英文逐个直接替换

优点：

- 上手最快
- 单次改动最少

缺点：

- 文案仍分散在几十个页面和方法里
- 后续补汉化时容易漏改和重复翻译
- 难以保持同一词汇口径一致

### 方案二：建立轻量统一文案层，再把现有页面和接口提示接入

优点：

- 改动规模仍可控，不引入完整 i18n 框架
- 后续继续补中文时只需补一处或少数入口
- 更容易统一状态词、按钮词和错误提示口径

缺点：

- 比纯替换多一层抽象
- 首轮需要花时间梳理文案分组

### 方案三：直接引入完整多语言资源体系

优点：

- 架构最规范
- 未来可扩展中英文切换

缺点：

- 明显超出当前需求
- 会把“汉化”扩展为一次中型重构

### 结论

采用方案二。

原因是它在不引入完整国际化框架的前提下，已经足够支撑这轮“全量汉化”的目标，也最符合当前仓库“先把真实产品体验做好，再控制改动范围”的方向。

## 总体设计

### 前端文案层

在 `openharmony/entry/src/main/ets/common/` 下新增一个轻量文案文件，例如 `UiText.ets`，用于集中维护用户可见文案。

文案按职责分组：

- `CommonText`：通用按钮词、状态词、加载词、空状态
- `DeviceText`：设备类型中文名、设备状态摘要回退词
- `RuleText`：规则页中的条件、动作、校验提示、摘要模板
- `NetworkText`：网络错误、连接失败、证书失败、请求超时等
- `PageText`：各页面特有标题和短语

不在这一步引入资源表驱动或动态语言切换，只提供常量和少量格式化函数，例如：

- “最后在线 {time}”
- “设备已绑定到 {room}”
- “场景执行成功”

### 前端页面接入方式

页面不再直接写英文用户文案，而是：

- 直接引用 `UiText.ets` 中的常量
- 或调用轻量格式化函数生成字符串

这样能保留当前页面结构，减少汉化带来的 UI 重写风险。

### API 错误映射

`ApiClient.ets` 仍然作为前端统一的接口错误入口：

- 保留对机器码的识别
- 把最终返回给页面展示的文案改成中文
- 把网络层错误也统一改成中文

这样页面层只需要继续显示 `err.message`，不用每个页面都自己做翻译。

### 后端返回文案

后端只改“会直接进入前端展示”的内容：

- `message`
- 应用标题
- 候选设备展示名
- 候选房间提示

后端不改：

- 机器码 `detail`
- 内部异常类名
- 仅用于开发排查的日志文本

## 文案规则

为避免同一产品里语气混乱，本次统一以下规则：

- 按钮用短中文动词：`登录`、`注册`、`保存`、`删除`、`刷新`
- 状态词统一：`在线`、`离线`、`加载中`、`扫描中`、`绑定中`
- 空状态尽量自然，不使用生硬直译
- 失败提示优先告诉用户下一步动作，例如“设备离线，请重新连接后再发送指令”
- 规则描述和设备描述优先用中文模板，不直接拼英文类型名

## 数据流与行为边界

### 前端

1. 页面触发请求
2. `ApiClient.ets` 请求后端
3. 若后端返回机器码或网络异常，`ApiClient.ets` 转成中文用户提示
4. 页面直接展示统一后的中文消息

### 后端

1. API 和服务层继续用原有机器码/逻辑做判定
2. 仅在返回给前端展示的 `message` 中给出中文
3. 测试如果只断言机器码则无需改动；如果断言英文 `message`，需要同步更新为中文

## 风险与处理

### 风险一：误改机器码导致前端映射或测试失效

处理：

- 明确只改用户提示，不改 `detail` 机器码
- 对规则、绑定、设备控制这几条链路做针对性回归

### 风险二：页面仍残留英文文案

处理：

- 以主页面和控制页为单位逐页检查
- 改动前后用文本检索再次扫描高频英文词

### 风险三：ArkTS 页面直接写字符串太多，改动分散

处理：

- 优先抽到 `UiText.ets`
- 仅在极少量局部文本上保留内联中文，避免为了“极致统一”大改页面结构

### 风险四：后端默认种子名称改动导致部分断言变化

处理：

- 先查看相关测试是否断言具体名称
- 若断言了展示名，则同步调整测试期望

## 验收标准

以下条件同时满足，才算这轮汉化完成：

1. 主页面、设备管理、远程控制、数据监控、规则页、个人中心、登录注册页不再向用户显示英文提示或英文主标题
2. 常见网络错误和接口错误以中文展示
3. 后端直接返回给前端显示的成功/失败消息改为中文
4. `rule_name_required`、`candidate_not_found` 等机器码保持不变
5. OpenHarmony 打包命令仍然成功
6. 受影响后端测试通过
