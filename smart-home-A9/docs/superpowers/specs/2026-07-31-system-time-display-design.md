# 手机系统时间显示设计

## 目标

OpenHarmony 客户端的所有用户可见时间统一跟随手机当前设置：

- 使用手机当前时区。
- 使用手机当前 12/24 小时制。
- 12 小时制的日间标记跟随系统语言环境。
- 不再在可见时间后显示 `UTC`。

后端数据库、接口字段和历史查询参数继续使用 UTC，避免改变现有时间契约。

## 范围

需要切换为手机系统时间的显示包括：

- 首页最后同步时间。
- 首页最近活动时间。
- 设备最近上报时间。
- 历史记录时间。
- 运行日志时间。
- 桌面服务卡片更新时间。

不修改页面布局、后端 API、数据库字段或 MQTT 消息格式。

## 显示规则

共享时间工具提供两个系统时间格式化入口：

- `formatSystemClock(date)`：只显示系统时钟。
- `formatSystemTimestamp(value, fallback)`：显示本地月日和系统时钟。

格式化时使用设备默认时区，不显式指定 `timeZone`。通过 API 20 的
`i18n.System.is24HourClock()` 读取 12/24 小时制，并使用系统语言创建
`Intl.DateTimeFormat`。

示例：

- 24 小时制：`15:09`、`07-31 15:09`。
- 12 小时制：`03:09 PM`、`07-31 03:09 PM`；具体日间标记由系统语言决定。

后端没有时区标记的 SQLite 时间仍按 UTC 解析。带 `Z` 或偏移量的时间按其明确时区
解析，再转换为手机时区显示。非法时间保留现有回退行为，不导致页面崩溃。

## 架构与数据流

共享时间工具继续统一管理三类职责：

1. 将后端 UTC、ISO `Z` 和带偏移量的字符串解析成同一个时间点。
2. 将该时间点按手机时区及 12/24 小时制格式化，用于所有可见时间。
3. 使用 `toUtcApiTimestamp` 生成后端历史查询边界。

显示数据流为：

```text
后端时间字符串 -> 按 UTC/显式偏移解析 -> Date 时间点 -> 手机系统格式 -> 页面文本
```

历史筛选数据流保持：

```text
手机当前时间 -> 计算时间范围 -> UTC API 字符串 -> 后端查询
```

这样显示会随手机设置变化，但查询结果不会因客户端时区而偏移。

## 组件修改

- 共享时间工具：增加系统时间格式化函数，保留 UTC API 序列化。
- `DashboardPage`：同步时间和最近活动改用系统时间格式。
- `DeviceManagePage`：最近上报改用系统时间格式。
- `DataMonitorPage`：历史记录和运行日志改用系统时间格式，查询边界仍为 UTC。
- `EntryFormAbility`：服务卡片更新时间改用系统时间格式。

各页面不自行实现时区或 12/24 小时制逻辑。

## 设置变化

格式化发生时读取当前系统设置。应用页面在重新进入、刷新或数据更新时重新格式化；
桌面卡片在手动刷新、系统更新请求或定时刷新时重新格式化。因此修改手机时区或
12/24 小时制后，不需要重新登录或清除数据。

## 错误处理

- 空时间使用调用方提供的回退文本。
- 非法时间保持原字符串或回退文本。
- 系统格式化异常时回退到基于本地 `Date` 字段的等价格式。
- 时间格式化失败不得阻断设备、历史记录或卡片数据加载。

## 测试与验收

自动化验证：

- 固定 UTC、SQLite、偏移量和小数秒输入，验证转换到指定本地时区。
- 分别验证 24 小时制和 12 小时制输出。
- 验证所有显示入口调用共享系统时间格式化函数。
- 验证历史查询仍调用 `toUtcApiTimestamp`。
- 运行完整 Python 测试和 API 20 Hvigor 构建。

模拟器验收：

1. 切换手机时区，刷新页面后确认所有可见时间同步变化。
2. 切换 24 小时制，确认显示为 24 小时格式。
3. 切换 12 小时制，确认显示为 12 小时格式并带系统日间标记。
4. 验证 24 小时和 7 天历史筛选仍能返回记录。
5. 刷新桌面卡片，确认更新时间与手机设置一致且无文字溢出。
6. 验证后端 `/api/ready` 仍返回数据库和 MQTT 正常。

## 非目标

- 不把数据库时间改成本地时间。
- 不改变后端时间字段或查询参数格式。
- 不增加用户自定义时区设置。
- 不修改现有页面布局。
